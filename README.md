# VaultTask Mobile

An Expo / React Native task app scaffold using the New Architecture, Expo Router, WatermelonDB, MMKV, Firebase, NetInfo, and a local biometric/encryption module.

## Architecture

- `src/app/` contains Expo Router routes; screen implementations live in `src/screens/`.
- Every screen has a dedicated `.styles.ts` factory, driven by the runtime brand token provider.
- WatermelonDB is the local source of truth. Mutations commit locally first and create an outbox entry in the same database writer.
- The sync worker batches queued Firestore writes and only removes outbox entries after a successful commit. Realtime remote updates are applied to the local database without overwriting pending local writes.
- MMKV stores the session cache, runtime brand, biometric preference, and last successful sync timestamp. Do not store passwords or Firebase refresh tokens in MMKV.
- `modules/native-secure-vault/` contains the local Expo native module. It provides biometric/device-credential authentication plus Android Keystore / iOS Keychain-backed AES-GCM encryption. It uses Expo's JSI-backed Modules API and is autolinked by prebuild.
- Android brand variants are generated by `plugins/withAndroidProductFlavors.js`. Native project output remains generated by Continuous Native Generation; do not commit manual edits under `android/` or `ios/`.

## Local development

1. Install dependencies with `npm ci`.
2. Copy `.env.example` to `.env.local` and provide Firebase project values. Firebase is optional for local guest mode; configure Email/Password and Anonymous providers and Firestore rules for remote use.
3. Generate native projects and run a development build (MMKV, WatermelonDB SQLite, and the secure vault require native code; Expo Go is not supported):

   ```sh
   npx expo prebuild
   npx expo run:ios
   # or
   npx expo run:android
   ```

4. Run `npm run typecheck` and `npm run lint`.

The local guest identity supports offline-only work. It is device-local and is not uploaded to Firestore. Sign in through Firebase while online to enable authenticated realtime and outbox sync.

## Android flavors and release automation

Prebuild creates the Gradle variants `retailDebug`, `retailRelease`, `enterpriseDebug`, and `enterpriseRelease`. Fastlane lanes are available via `bundle exec fastlane android retail`, `enterprise`, and `all_brands`. Build both release variants with `./gradlew assembleRetailRelease assembleEnterpriseRelease --max-workers=1` to avoid D8 heap pressure when flavor dexing runs concurrently. Configure CI-managed signing before publishing release artifacts; the scaffold intentionally contains no keystore or signing credentials.

GitHub Actions runs typechecking, lint, native prebuild, and both Android release variant assemblies. A manual `workflow_dispatch` also uploads both variants to Firebase App Distribution when the repository has `FIREBASE_SERVICE_ACCOUNT_JSON`, `FIREBASE_APP_ID_RETAIL`, and `FIREBASE_APP_ID_ENTERPRISE` secrets configured. Optionally set the `FIREBASE_DISTRIBUTION_GROUPS` repository variable. The service account needs Firebase App Distribution administrator permissions. Add Firebase configuration and signing secrets to the deployment environment only; never commit them.

## Security notes

The vault encrypt/decrypt APIs protect values at rest, and biometric authentication gates app access. Authentication does not imply that arbitrary task content is encrypted in SQLite. For sensitive production workloads, define a threat model and encrypt selected fields before persisting them, including key rotation, backup, and biometric enrollment-change behavior.
